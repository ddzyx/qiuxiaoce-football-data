# Skill 更新（updating）

## 适用意图

仅在用户明确提出"检查更新"或"更新 Skill"时执行。**不在普通查询、写作或分析任务中自动更新。**

## 标准流程

1. 运行 `python scripts/update_skill.py --check` 查看远端版本。
2. 有新版本时，向用户展示版本号与 changelog，等用户确认。
3. （可选预演）运行 `python scripts/update_skill.py --dry-run`：下载并校验更新包但不切换目录，输出会列出将被归档的本地修改与将被保留的新增文件。
4. 用户确认后运行 `python scripts/update_skill.py --apply`。

更新脚本内置的安全保障（无需你额外操作）：

- 语义化版本比较，同版本或更低版本默认拒绝（排障时才用 `--force`）；
- 拒绝绝对路径、`..` 越界路径、符号链接和不在白名单内的文件类型；
- 单文件与总包大小限制；
- 服务端 SHA-256 文件清单逐一校验，包内 SKILL.md 版本与服务端版本一致性校验；
- 更新前整目录备份到 `../skill-backups/`，失败自动回滚。

## 本地定制的保留策略

用户修改或新增 Skill 文件是允许的，更新不会 silently 丢失这些改动：

- **用户新增的文件**：更新后自动恢复到新版本目录中，原样保留；
- **用户修改过的官方文件**：更新后以官方新版为准，用户的旧版归档到 `local-overrides/` 对应路径下，并在更新结果中列出；
- 脚本通过 `.qiuxiaoce-manifest.json` 记录上次更新的官方文件哈希基线，据此区分"官方改动"和"用户改动"；首次执行结构化更新时，与新版不一致的旧文件一律按本地改动归档，确保安全；
- 建议用户把个性化内容放在新增文件中，而不是直接改官方文件。

## 冲突的 LLM 仲裁流程（必须执行）

当 `--apply` 输出中 `modified_files_archived` 非空时，不得直接结束，必须继续完成冲突仲裁：

1. 运行 `python scripts/update_skill.py --diff`，获取每个冲突文件「我的版本 vs 官方新版」的统一差异。
2. 由你（LLM）逐个分析差异的语义：用户改了什么、官方改了什么、两者是否可兼得。
3. 用简明中文向用户逐文件汇报分析结论，并给出三个选项：
   - **采用官方新版**（放弃我的改动）；
   - **恢复我的版本**（覆盖官方新版）；
   - **手动合并**（由你直接编辑官方新版文件，把用户的改动合并进去）。
4. 按用户答复执行：
   - 官方新版：`python scripts/update_skill.py --resolve <文件> --choice official`；
   - 我的版本：`python scripts/update_skill.py --resolve <文件> --choice user`；
   - 手动合并：编辑该文件完成合并后，再执行 `--resolve <文件> --choice official` 清除归档。
5. 全部处理完毕（`remaining_conflicts` 为空）后，向用户确认更新完成。
6. 用户不在场或无法确认时，默认采用官方新版并保留归档，明确告知用户可事后用 `--diff` / `--resolve` 重新处理。
